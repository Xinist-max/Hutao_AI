# 对话上下文连贯性

> 这一节记录三类问题的排查与修复：**会话被拆成两条线**、**冷却递减的 60 倍单位错误**、
> **全系统的时间模型**。第三部分尤其重要——单位错误都很隐蔽，这张表是防复发用的。

---

## 一、会话被拆成两条线（已修）

### 现象

用户问「你忘了昨天晚上咱们做什么了？再好好找找上下文呢」——她答不上来，只能编。

### 根因

引擎的主动发言和用户的直聊**写进了两个互不相通的会话**：

| 会话 key | 装了什么 |
|---|---|
| `agent:main:liyue-scene-{date}` | 只有引擎注入的事件 + 她的回复，**一条用户消息都没有** |
| `agent:main:openclaw-weixin:direct:YOUR_ACCOUNT` | 只有用户的直聊 + 她的回复，**一条主动发言都没有** |

后果：她主动发给用户的话，**不在她回答用户时的上下文里**。用户回她时，她看到的是一段
没有前因的对话，于是只能编一个听起来合理的答案。

### 修法

`config.sessions.json` 的 `session_key` 改成 `{user_session}`——引擎把事件投到
**和用户直聊同一条会话**，形如：

```
[user]      你忘了昨天晚上咱们做什么了？
[assistant] （愣了一下…）本堂主……本堂主当然记得
[user]      【引擎注入】[璃月港事件] 午后码头：…
[assistant] 诶，今天的码头风挺大的呢~（眯着眼笑）
```

她的主动发言成为会话历史的一部分，用户回她时她看得见，**双向都对得上**。

**代价**：上下文变长（实测约 2.2 万输入 token/次）。本地模型免费、云端计费。
想省 token 可以改回 `agent:main:liyue-scene-{date}`（按天隔离），但要接受连贯性丢失。

> 注入的事件在会话里是 `user` 角色消息，靠 `[璃月港事件]` 前缀与真人发言区分。
> 这个前缀是刻意的：它读起来像"璃月港里发生了一件事"，而不是"用户说了什么"，
> 也不含「系统/指令」这类会诱导模型出戏的词。

## 二、冷却递减的 60 倍单位错误（已修）

### 现象

`welcome_back`（"你终于回来了"）实际投递 **187 次**，间隔中位数 24 分钟、最小 12 分钟，
**153 次间隔不足 1 小时**。而她反复说同一句话，连贯性被彻底破坏。

但它配的是 `cooldown_minutes: 720`（12 小时）+ `user_inactive_hours_min: 24`。

### 根因

```python
# scene/engine.py（修复前）
for k in list(s.cooldowns):
    s.cooldowns[k] -= minutes      # minutes = 30，是 tick 的「场景分钟步长」
```

而真实时间是**每 30 秒一个 tick**（`tick_interval_seconds: 30` / `tick_minutes: 30`）。
按步长扣 = **快了 60 倍**：720 分钟的冷却 24 个 tick（12 真实分钟）就耗光，
与实测"最小间隔 12 分钟"完全吻合。

### 修法

```python
elapsed = real_minutes if (sync_to_utc8 and real_minutes) else minutes
for k in list(s.cooldowns):
    s.cooldowns[k] -= elapsed
```

同步模式下按**真实经过时间**扣（`real_minutes` = `tick_interval_seconds / 60` = 0.5）。
非同步的演示模式保持原样——那种模式下场景时间本就快跑，以场景分钟为准是对的。

**实测**：同步模式 720 冷却 = 1440 tick = 720 真实分钟 = **12.0 小时**（修复前 12 分钟）。

### 影响

| | 修复前 | 修复后 |
|---|---|---|
| idle 模板（冷却 180~300 分钟） | 3~5 **真实分钟** | 3~5 **小时** |
| 实际发言节奏 | 几乎不停嘴 | 约 1 条/小时（防沉默阈值 60 分钟 + 决策层 20~90 分钟区间把关） |

## 三、全系统时间模型（防复发）

这套系统里同时存在**两个时钟**，混用就会出上面那种 60 倍错误：

| 时钟 | 含义 | 何时两者相等 |
|---|---|---|
| **真实时间** | Unix 时间戳、`tick_interval_seconds` | — |
| **场景时间** | `day * 1440 + hour * 60`，即 `scene_minutes()` | **`sync_to_utc8 = true` 时与真实时间相等**（按北京时间对齐） |

| 机制 | 用哪个时钟 | 单位基准 |
|---|---|---|
| 决策层推送节奏 `_next_allowed`（20~90 分钟） | **真实时间**（`time.time()`） | 真实分钟 ✓ |
| 冷却扣减 `s.cooldowns[k] -= elapsed` | **真实经过时间**（同步模式） | 真实分钟 ✓ |
| `anti_silence_minutes`（60） | 场景时间 | 同步模式下 = 真实分钟 ✓ |
| `follow_up_minutes`（90） | 场景时间 | 同上 ✓ |
| 回执冷却 `receipts.py` 存 `scene_minutes()` 与 `scene_now` 比较 | 场景时间对场景时间 | 一致 ✓ |
| `decision.suppress_after_user_minutes` | 真实时间（`state.last_user_message_ts`） | 真实分钟 ✓ |

**判断原则**：两个量相减/比较时**必须是同一个时钟**；而"每 tick 扣多少"这类**递减量**，
必须用**真实经过时间**，不能用 tick 的场景步长——否则快慢就取决于 `tick_minutes` 与
`tick_interval_seconds` 的比值（当前是 60）。

### 排查这类问题的快捷方法

```bash
# 实际投递间隔 vs 配置的冷却，不一致就是单位错了
python3 -c "
import json, datetime as dt, statistics
ts=[dt.datetime.fromisoformat((json.loads(l).get('ts') or '')[:19])
    for l in open('logs/harbor.jsonl',encoding='utf-8')
    if '\"delivered\"' in l and 'welcome_back' in l]
ts.sort()
gaps=[(ts[i]-ts[i-1]).total_seconds()/60 for i in range(1,len(ts))]
print('间隔中位数', statistics.median(gaps), '分钟；最小', min(gaps))
"
```

## 四、动作连贯性（她不会重复同一个动作）

### 问题

她把动作写在全角括号里（`（叉腰）`、`（把帽子摘下来）`），但**模型只把它当装饰性文字**，
不当成"状态改变"。实测历史里 155 处动作的分布：

| 动作 | 次数 |
|---|---|
| 眯着眼笑 | **13** |
| 更小声 / 声音轻下去 | 各 9 |
| 闷声，带着点委屈 | 8 |

两种洋相：**重复**（上一段刚摘帽子、下一段又摘一次）和**自相矛盾**（没戴帽子却说扶正帽檐）。

### 做法：`scene/actions.py`

| 机制 | 作用 |
|---|---|
| **最近动作** | 记最近 10 个动作，注入时只给最近 3 个并标明"别重复" |
| **持续状态** | 关键词规则推断帽子摘/戴、坐着/站着、抱着/松手，跨消息保持 |
| **两条时效** | 状态 6 小时、最近动作 2 小时——隔太久就不该再断言"当前坐着""刚用过" |

注入形态（**只占 20~58 字符**，因为会写进历史）：

```
【动作连贯】刚用过（别重复）：托腮笑、把围巾往你那边拉一拉；当前帽子戴着；当前坐着（要站得先写起身）
```

### 局限（有意为之）

中文动作表达千变万化，正则做不到全懂。所以规则表只覆盖**最明确、最容易出洋相**的几类，
其余靠"最近动作去重"兜住——**宁可少断言，不要错断言**。
规则表在 `_STATE_RULES`，加一类状态就是加一行。

### 实测

回填历史 47 条回复 → 抽出 159 处动作，推断出「帽子戴着 / 坐着 / 抱着」。
随后一次真实投递里她用的是 `（侧身往窗边靠了靠）`、`（把围巾往你那边拉一拉）`、`（托腮笑）`——
**均非历史高频动作**，也没有与帽子状态冲突。
