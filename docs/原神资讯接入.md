# 原神实时资讯接入（版本 / 卡池 / 剧情 / 节日）

> 目标：让胡桃知道"现在提瓦特发生了什么"，而不是永远活在写死的 47 条模板里。

## 一、先解决的矛盾：元游戏 vs 世界内

官方资讯是**元游戏**的——版本号、卡池、祈愿、概率UP、原石、纠缠之缘，
全是玩家视角的系统词汇。而胡桃是**活在璃月港里的人**，
她一张嘴说"这期卡池"，第四面墙就碎了
（`SOUL.md` 的「没有什么隔着我们（器物层）」那一节费了多大劲才把墙砌好）。

所以本模块**不做"把资讯喂给她"，而是做一层世界内翻译**：

| 现实资讯 | 翻译成她能经历的 |
|---|---|
| 7.1「往冥府的安魂歌」 | 港里、行商之间在传的一件和这四个字有关的怪事 |
| 卡池 UP 薇斯纳(风) | 跑商的回来说港里来了个使风的外乡人 |
| 卡池 UP 沃雅妮莎(水) | 同上，玩水的一把好手 |
| 魔神任务「无神怜爱的雪国」 | 走远路的商队从雪国回来，说那边出了大事 |
| 六周年 | 璃月港格外热闹，到处在张罗一场大庆祝 |
| 逐月节（农历八月十五前后） | 璃月自己的节：张灯结彩，堂里的活计换了路数 |

**所有生成的事件都走「传闻」框架**（跑商的说的 / 港里都在传 / 听人讲）——
这样她复述一个**只知道姓名和元素**的外乡人时，天然不需要编造性格，
既不胡吣，也不出戏。

措辞上也做了统一约束：`_rumor_instruction()` 会把
`版本/卡池/祈愿/概率UP/原石/纠缠之缘/抽卡/保底/十连/命座/圣遗物/深渊`
这一串**逐条列进指令的禁止清单**，明确告诉她"你根本不知道这些是什么"。

## 二、数据源

**米游社官方公告 API（CN 服，无需鉴权）**：

```
https://hk4e-api.mihoyo.com/common/hk4e_cn/announcement/api/getAnnContent
  ?game=hk4e&game_biz=hk4e_cn&lang=zh-cn&bundle_id=hk4e_cn
  &platform=pc&region=cn_gf01&level=60
```

一次返回约 36 条公告（版本说明、卡池公告、活动、魔神任务、世界任务）。
**只解析 `title`，不读几百 KB 的 `content` 正文**——标题里信息已经够了。

实测过的备选，都不可用或不够：

| 源 | 结果 |
|---|---|
| `api.ennead.cc/mihoyo/genshin/calendar` | 本机**连不通**（HTTP 000） |
| `api.hakush.in/gi/data/...` | 本机**连不通**（HTTP 000） |
| `gi.yatta.moe/api/v2/...` | 通，但只有角色/武器数值，**没有版本与卡池层信息** |
| `getAnnList`（公告列表） | 通，但**活动公告分类恒返回 0 条**；`getAnnContent` 才有内容 |

### SSL：本机 Python 的坑

本机是 python.org 版 Python 3.14，**默认信任库是空的**——
直接 `urlopen` 会 `CERTIFICATE_VERIFY_FAILED: unable to get local issuer certificate`，
而同一条 URL 用 `curl` 却正常（curl 读系统钥匙串）。

`scene/news.py` 的 `_ssl_context()` 按顺序找可用 CA：
`certifi` → `/etc/ssl/cert.pem`（macOS 系统）→ 默认。两者实测都可用。

> 项目里其他工具只用 `urllib` 连 localhost（ComfyUI 8188、Ollama），不涉 SSL，
> 所以这个坑是接入外部 HTTPS 时才第一次踩到。

## 三、节日的推导方式

公告标题**不一定会带上节名**（7.1 那批只有"溯月"系列，没有"逐月节"三个字），
所以节日**用现实日期窗口兜底推导**（`current_festival()`）：

| 节日 | 窗口（公历近似） | 归属 |
|---|---|---|
| 海灯节 | 1/20 ~ 2/20（农历正月初一前后） | 璃月 |
| 逐月节 | 9/10 ~ 10/10（农历八月十五前后） | 璃月 |
| 风花节 | 3/1 ~ 3/31 | 蒙德 |
| 羽球节 | 10/1 ~ 10/31 | 蒙德 |

标准库做不了农历换算，所以是**近似窗口**，产出里带 `approx: True` 标明。
大体上"中秋前后就是逐月节、春节前后就是海灯节"这个映射是稳的。

**璃月的节和外地的不一样对待**：璃月的是 `priority="high"`、冷却 1 天、
要她讲"这两天实际在忙什么"；外地的降到 `medium`、冷却 7 天、当谈资。

## 四、文件与用法

| 文件 | 作用 |
|---|---|
| `scene/news.py` | 抓取 + 解析 + 缓存 + **世界内翻译**（核心） |
| `tools/genshin_news.py` | 命令行外壳 |
| `logs/genshin_news.json` | 缓存（6 小时 TTL，运行时产物） |

```bash
python3 tools/genshin_news.py                # 拉最新资讯并显示
python3 tools/genshin_news.py --events -v    # 看翻译出的世界内事件 + 完整指令
python3 tools/genshin_news.py --force        # 忽略缓存强制重拉
python3 tools/genshin_news.py --offline      # 只读缓存，不联网
```

引擎侧在 `main.py` 的 `load_all_templates()` 接入：
静态 `events.json` ＋ 资讯翻译出的事件，**失败只降级为"少几条时令事件"**，
绝不阻断主链路（网络断了、API 改版了，她照常活在原来那 47 条里）。

配置（两个 config 的顶层 `news` 块）：

```json
"news": { "enabled": true, "cache_hours": 6, "timeout": 20 }
```

## 六、⚠️ 测量陷阱（别再踩）

排查"资讯事件从不触发"时，我先后得出过**两个错误结论**，都是仿真环境的问题：

### 陷阱一：`sync_to_utc8=True` 时，仿真循环里的场景时钟是停的

`SceneState._sync_to_real_time()` 读的是 `datetime.now()`（真实钟表），
**完全不管 tick 传进来的 `minutes`**。仿真循环秒级跑完 20,000 个 tick，
场景时间却**始终停在启动那一刻**（实测卡在 23:57）。

后果：资讯事件的 hours 窗口是 9-23 / 11-22，**在 23.9 点全部不够格**；
只有夜间事件（`moon_night`/`good_night`/`ghost_chatter`/`stargazing_night`）能触发。
看起来就像"资讯事件永远轮不上"，其实是**仿真里根本没有白天**。

正确做法——把同步时钟换成会走的假时钟：

```python
def fake_sync(self):
    self.hour += tm / 60.0
    while self.hour >= 24.0:
        self.hour -= 24.0; self.day += 1
SceneState._sync_to_real_time = fake_sync     # sync_to_utc8 仍为 True，保留冷却语义
```

换成假时钟后，同样的代码立刻测出 190 次资讯事件。

**以后任何引擎行为的长时程仿真，都必须先确认时钟真的在走**
（打印 `st.hour` 看它有没有变）。

### 陷阱二：冷却按真实分钟扣，短仿真只剩"启动爆发"

`tick()` 里冷却扣的是 `real_minutes`（生产 0.5 分钟/tick），不是场景步长。
所以 400 个 tick 只相当于 **3.3 分钟真实时间**——所有模板在前几个 tick 连发一轮
之后就全部进冷却，后面几百个 tick 静默。看到的现象是"只有 5 个模板、事件很少"，
但那不是引擎的问题，是**仿真太短**。

生产要跑几天，仿真就得按几天算（20,000 ticks ≈ 7 真实天）。

### 顺带纠正一个**不成立**的结论

排查中我曾断定"引擎按列表顺序扫描，导致 append 在末尾的模板被饿死 42 条"，
并据此改过 `scene/engine.py`。**这个结论是错的，改动已回退。**

真实情况：
- 那 42 条不触发的模板，原因是**条件门控**——其中 23 条是 NPC 在场事件
  （需要钟离/魈/温迪等同时在场），其余是 `follow_up_*`（靠话题机制触发）和特定时辰事件；
- 洗牌 vs 顺序扫的 A/B（假时钟、7 天时程）结果：**资讯事件都是 190 次，
  模板种类都是 27 种，事件总数 4820 vs 4834**——洗牌没有任何可观测收益。

**结论：资讯接入不需要改引擎。** 生产行为分毫未动。

# 七、见闻不许打断对话（对话缓冲）

接入资讯之后暴露的问题：**她会在长对话中途冷不丁冒一句见闻**。

场景是这样的——用户和她正围绕某个话题一来一回，中途用户去倒了杯水、
或者停下来看了会儿消息（几分钟）。此时原有的「用户刚发消息 3 分钟内不插嘴」
已经过期，引擎就把一条时令见闻（「港里来了个外乡人」）推出去，**话题被硬生生打断**。

更糟的是：逐月节那条是 `priority="high"`，而原规则**对高优先级直接豁免**——
高优先级恰恰是最容易"冷不丁冒出来"的那类。

## 两道时间闸

| 配置（在 `decision` 块） | 默认 | 作用 |
|---|---|---|
| `conversation_buffer_minutes` | 20 | 双方**任一方**最近开口后 N 分钟内，**一条主动事件都不产生** |
| `news_hold_minutes` | 60 | 带 `news` 标签的时令事件，在对话结束后再压这么久 |

判据是**任一方**最后开口的时间（`state.last_conversation_ts`），不是只看用户：
用户说完、她回完，对话**仍然是热的**。只看用户发言的话，用户沉默几分钟就被
误判成"人走了"——这正是问题根源。

**第一道闸不看 `priority`**：高优先级同样被压住。

## ⚠️ 为什么闸必须放在引擎里，不能放在决策层

这是本次最关键的一个坑。

原来的链路是：`engine.tick()` → `_fire()` → **先扣冷却** → 交给 `decision.decide()`。

也就是说，**被决策层挡下的事件，冷却已经消耗掉了**——"没发出去但报废了"。
时令见闻的冷却是 **3~7 天**，在决策层挡一次，就等于**永久丢掉那条见闻**。

所以两道闸都实现在 `scene/engine.py` 里，**在开火之前拦**：

- 第一道：`tick()` 在演化完时钟/天气/在场/冷却之后、选事件之前 `return []`
  （放这个位置而不是函数最开头，是为了**缓冲期内场景照常演化**，只是不开口）
- 第二道：`_suppressed()` 里对带 `news` 标签的模板返回 `True`
  ——是"根本没选它"，冷却不会白扣，静默期过了照样能发

配置值仍然写在 `decision` 块（**单一调参入口**），由 `main.py` 传给引擎构造函数。
`scene/decision.py` 里保留了字段定义和一段指路注释，没有执法代码——
同一条策略只留一个实现，否则调参会调漏。

## 顺带修掉的一个隐藏缺陷

原来"从会话同步用户最后发言"这段逻辑埋在 `apply_affinity_decay()` 里，
而那个函数在 `decay_enabled=false` 时**会提前 return**——衰减一关，
两个判据（用户发言、对话活动）就永远不更新，「不插嘴」和「对话缓冲」全部失效。

现已抽成独立的 `sync_conversation_activity()`，**每 loop 无条件调用**，与衰减解耦。

另外，会话转录读取做了 `(路径, mtime, 大小)` 缓存：转录文件会一直变大，
每 loop（30 秒）无脑重扫一遍是白烧 CPU，文件没变就直接复用上次结果。

## 验证

假时钟固定时间戳，60 个 tick 一轮（`quiet_buffer=20 / news_hold=60`）：

| 静默时长 | 普通事件 | 资讯事件 | 资讯冷却被扣 | 结论 |
|---|---|---|---|---|
| 2 min（对话正热） | 0 | 0 | **0** | 缓冲期内一条都不出，且**没白扣冷却** |
| 30 min | 11 | 0 | **0** | 缓冲已过、见闻静默中：可出普通、不出资讯 |
| 90 min | 11 | 6 | 5 | 两道闸都过了，资讯正常出现 |
| 600 min | 15 | 6 | 5 | 同上 |

开关对照（同样静默 2 分钟）：关闭 → 17 条（恢复原行为）；打开 → 0 条。
冷下来后（600 min）开关开/关结果一致（21 = 21）——**这个功能只影响对话热的时候，
其余情况分毫不动**。

> 测试时踩过一个坑：把 `time.time` patch 成 `0`，而状态里的时间戳是 `1.8e9`，
> 于是 `minutes_since_activity()` 恒为 0（永远在缓冲里），看起来像"缓冲把一切都挡了"。
> **假时钟必须和被测状态的时间戳在同一坐标系**。
